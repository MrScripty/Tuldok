# General canonical COCO detection

The existing canonical release owner serializes current `image_detection` annotations to `train/coco.json`, `validation/coco.json` and `test/coco.json`, alongside the unchanged canonical manifest and assets. This is a qualification and small UI/error repair of that workflow, not a competing schema or new training pipeline.

Each reviewed record has at most500 boxes. Labels are exact strings of at most80 Unicode code points. Boxes retain finite, positive, in-bounds pixel-edge `x,y,width,height`, including fractional/subpixel values; overlaps and repeated categories are allowed. Zero extent, booleans, nonfinite values, duplicate identical boxes and unrepresentable numeric coordinates fail through the existing typed error owner before mutation. The editor uses arbitrary numeric steps and allows positive sizes below1; Save enforces strict positivity. An explicitly reviewed empty box list is a detection negative. Draft or missing annotations remain ineligible.

The complete selected detection vocabulary is sorted by exact Unicode label and numbered1..N. All three split files share that category table. Reordering the same selection does not change IDs or ZIP bytes; subsetting or relabeling can renumber IDs. No persistent/global taxonomy is claimed. Original imported category tables and ordered source category IDs remain provenance, separate from current local labels. Image IDs follow sorted canonical manifest rows; annotation IDs restart at1 in each split. Boxes use `bbox: [x,y,width,height]`, `area: width*height`, and `iscrowd: 0`. No polygon, segmentation truth, tracking or crowd behavior is added.

Selections remain bounded5,000 records with the existing image normalization/pixel limits and500 boxes per detection record. Canonical releases may include other typed tasks under existing serialization rules; there is no new universal40MiB canonical-image archive budget. Existing allocator rules include unselected/deleted family bridges and fixed source splits. Empty split files are permitted by the existing profile (including an all-negative train-only profile); this is distinct from the narrower Chapter9 adapter's all-three-nonempty, integer single-box contract.

The rendered workflow retains existing explicit draft save, separate review, exact revision/source selection pairs, fresh preview proof, atomic freeze, immutable download and history. Inspection/preview shows release-local category IDs using safe text. Imported canonical detection ZIPs begin as new local records with draft review and unknown rights; source provenance does not grant local approval. Import supports the existing strict native canonical format, not arbitrary foreign COCO. Native interop QA uses bounded8MiB physical/16MiB expanded packets,1..100 images,40MP/image and100MP total; these are consumer-test limits, not a general canonical output promise.

Qualification independently verifies asset/pixel hashes, oriented dimensions, exact source targets/review/provenance, category/image/annotation associations, fractional geometry, negatives and family allocation before actual pycocotools2.0.11 and torchvision0.23.0 reads. Source/package identities are pinned in `tests/fixtures/coco-consumer-pins.json`; the official COCO index itself is permissive and does not replace validation. The same retained six authored PNGs and simulated review actions support source and two-owner rendered roundtrips; they are not a real labelled benchmark. No model, optimizer, mask conversion, evaluation, training, weights or data download executes. UI provisional.
