## Composed-design review: applicable

1. Concerns/dimensions: Workbench stores independent human-authored targets/history for text prompt IDs when explicit CAS saves occur; UI presents and edits them on a loaded record; Releases freezes selected units for consumer use; the verification harness qualifies the actual projection independently. All use existing local Dataset ownership, not a new service.
2. Interleavings: response ID/prompt ID and exact value are domain facts; review/revision/time are response-owned. Source and response state interleave only at checked save and frozen release. UI request epochs/selection intent remain transient. Repeated create IDs conflict and failed history writes roll back atomically.
3. Caller knowledge: declared response-save and fixed-selection fields, dedicated format and ordinary failure codes. App routes delegate to Workbench/Releases; callers do not know SQL/staging/graph internals. Consumer rows know only prompt/completion; sidecar owns revision/family mapping. Verification-only Python/dependency environment is explicit.
4. Change locality: response semantics touch Workbench and response editor/contracts; family semantics touch the shared graph/allocator; consumer projection changes touch Releases and the byte-pinned checker; deployment/identity stay existing-owned. A future preference/conversation contract requires new admission, not generic annotation migration.
5. Dependencies: parent record/source/response IDs, exact revisions and format are stable serialized interfaces. Workbench SQLite representation is private. App shares the existing lock/connection. Local frontend reuses the existing api/current/notice hooks; startup loads the response script after workbench.js. This ordering is explicit and page-load/browser tested.
6. Independent evolution/failure: response history/CAS tests do not depend on browser or consumer packages; consumer gate does not depend on provider jobs or training. Renderer failures cannot publish review. Failed exports clean staging and preserve prior ZIPs. Existing record selections/formats stay independent.
7. Deletion test: deleting response rows/history loses simultaneous targets/audit; moving them into generic annotation would reintroduce replacement conflicts. Deleting fixed response pairs loses exact intent. Deleting the adapter pushes task-specific projection into callers and discards canonical evidence. Deleting the shared family helper duplicates existing graph policy. The resource check contains bounded synchronous publication. Deleting the new UI removes the user-facing path. The verification-only consumer checker is retained while the pinned compatibility claim exists; replacing the consumer requires new pin/qualification. No registry/queue/framework is introduced.
8. Inherent complexity: independent revisions, exact Unicode, review, transitive source families, weighted examples, immutable publication and delayed UI intent are necessary. Workbench, shared allocation/preparation, one dedicated frontend and one independent consumer harness contain it. Fixed-selection file storage reuses browser file/download primitives and does not extend/migrate existing record sets.
