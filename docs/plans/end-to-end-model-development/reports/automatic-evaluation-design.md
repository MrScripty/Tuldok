# Independent design assessment: automatic evaluation and reuse

Date: 2026-10-15. Scope: questions that change the proposed end-to-end architecture. This is evidence and acceptance guidance for **designing** that architecture, not an implementation plan or a dependency decision. No application behavior changed.

## What “automatic” must mean

For a supported model/task, selecting data, a model definition and a training budget should select an appropriate evaluation profile too. Starting the run should produce its declared scalar histories, fixed-probe observations and suitable views without a user adding logging calls, importing predictions, wiring a separate evaluation graph, or configuring plots for every run. First integration of a custom model or scientific evaluator still requires an author to declare its semantics. A default is useful only if its resolved values and costs become part of the frozen run definition.

There are three distinct responsibilities: the producer measures and emits evidence; the owner validates, retains and serves it; the UI projects admitted capabilities into useful controls and views. A chart cannot recover predictions that the producer never saved. Evaluation-only replay is a separate execution with its own identity, cost and authorization.

## Evidence and design decisions

| Evidence | Design consequence | Necessary design work | Optional machinery |
| --- | --- | --- | --- |
| [Image worker](../../../../image_training.py) retains epoch scalar history and only the selected checkpoint's prediction rows. The [image contract](../../../contracts/workspace-image-training.md) has a closed six-file inventory and 1–5 epoch bound. | Completed-run curves can already be projected. A checkpoint-by-example visual history requires new production/retention semantics; it cannot be inferred from loss history. | Specify bounded checkpoint/probe index, exact producing checkpoint, post/pre-update semantics, inference recipe and artifact identity. Define a compatible adapter version and historical-read behavior. | Live field streaming, retaining every checkpoint, full optimizer state and resumable training. None is required to retain a few meaningful evaluation points. |
| [Text](../../../../text_training.py) and [audio](../../../../audio_training.py) each publish one fit result; [Rheon CPU fitting](../../../contracts/rheon-cpu-training.md) is closed-form with zero optimizer steps. | One common screen must support several training processes without inventing epochs, gradients or updates. | Separate fit pass, optimizer update, examples/tokens processed, physical time and wall time. Declare which clocks and observations exist. | A universal optimizer telemetry schema covering every internal parameter. Start with common observations and explicit extensions. |
| [Generic recipes](../../../contracts/external-recipes.md) capture exact definitions/runtime/inputs, verify declared bounded outputs and expose the latest valid progress event. [Runs](../../../../runs.py) checks bounded summaries rather than interpreting arbitrary model meaning. | Generic execution is reusable; latest-event progress is not durable history or scientific acceptance. | Decide whether history is an indexed artifact, bounded append protocol or both. Bind metric definitions/direction/units, split/probe membership, transforms and evaluator implementation. Keep exact-byte integrity distinct from domain validity. | A new execution engine, second artifact store or independent training supervisor. Existing owners should be the default comparison alternative. |
| Existing [Runs UI](../../../../static/workspace-real.js) already connects confusion counts to frozen prediction references and current Data correction. | Extend that loop with automatic task views; corrections must preserve prior evidence. | Specify capability-to-view rules, compatible comparison admission, actor/catalog/run scoping, stale-response behavior and exact frozen media access. | Separate standalone dashboards, per-run chart builders or users manually importing artifacts. |
| [Scientific field inspection](../../../../static/scientific-fields.js) uses a single record and per-slice range; native pressure evaluation has solver-specific operators and field stages. | Numeric arrays alone cannot determine safe alignment or physical correctness. | Specify domain-owned field pairs, grid/time/centering/stage/unit/mask compatibility, reference/prediction shared scales and separate error scales; reject or explicitly declare transformations. | Universal 3D rendering, mesh resampling, probabilistic field coverage and new native numerical methods. A synchronized slice comparison can answer the first question. |

The capability model should distinguish **supported**, **selected/enabled**, **scheduled**, **observed**, **verified** and **available to this viewer**. These are separate facts. View states additionally need not-applicable, not-configured, not-yet-produced, skipped-by-budget, failed, interrupted/partial, missing/corrupt, incompatible, historical-version unsupported and test-exposure required. Zero is a measured value, not a replacement for any of them. A successful run can have unsupported uncertainty or unavailable historical checkpoints; the design must say whether missing *required* evaluation fails admission/completion or produces an explicit incomplete result.

## Acceptance scenarios the design must make concrete

These are eventual behavioral acceptance examples; this design task should specify their evidence and boundaries rather than implement them now.

| User action with no additional evaluation setup | Required evidence and visible behavior | Boundary demonstrated |
| --- | --- | --- |
| Choose a supported image template, an eligible frozen release and three epochs; start training. | Default profile freezes reproducibly chosen validation probes and a bounded cadence. At least two actual checkpoints have retained predictions on identical probe identities. After restart the user can select one example, compare probabilities across checkpoints, and inspect frozen input/target with the selected-checkpoint marker. | A first model integration can configure instrumentation once; an ordinary run needs no custom callback or plot wiring. One epoch truthfully gives one observation. |
| Choose the existing text or audio classifier and fit once. | Appropriate validation confusion/per-class/probability and example evidence appears automatically. Text preserves its actual text preprocessing; audio inspection binds exact source channel, frame interval and sample rate. The process is shown as one fit. | No fabricated neural learning curve, gradient trace or repeated-seed uncertainty. |
| Choose an admitted iterative scientific pressure template and a bounded probe profile. | Same field cases appear at actual retained checkpoints; physical time has its own control. A prediction with one tenth the target amplitude remains visibly different under a shared scale. Native residual/corrected-divergence evidence names its operator/gauge/stage. | No silent collocation, resampling, gauge alignment or assertion that plausible appearance means numerical acceptance. A closed-form scientific model shows one fit instead. |
| Repeat or compare two runs; then correct an erroneous current annotation. | Comparisons show matched frozen cases/semantics and identify changed inputs. The correction creates new current evidence for a future freeze; old predictions remain unchanged. Test-derived plots, counts and previews require the relevant exposure path. | Cross-release changes do not become controlled improvements, and an exposed family is not fresh merely because its archive changed. |
| Select a custom model lacking a probe producer. | Before execution the UI identifies supported versus missing evaluation capabilities and the integration needed. Existing scalar or final-output views remain usable where valid. | No claim of zero-integration support for arbitrary models; no silent disappearance of required default evidence. |
| Request a bounded tuning study. | The design records search space, resolved trial parameters, objective/constraints, fixed validation protocol, trial/aggregate compute and storage caps, cancellation/failed-trial semantics and final selection provenance. | Tuning never selects on test evidence or exceeds the approved study envelope; each child run retains ordinary execution custody. |

## Meaningful alternatives and tradeoffs

The [verified software precedents](../../training-evaluation/reports/software-precedents.md) establish that these patterns exist; they do not establish equivalent immutable custody, arbitrary-domain coverage or a universal visual model editor.

| Alternative to evaluate in the design | Benefit | Cost or limit to resolve | Design recommendation |
| --- | --- | --- | --- |
| Tuldok orchestrates existing annotation, release, Pipeline and Runs owners with task adapters. | Preserves current identities, exact artifacts, authorization and correction flow; can cover custom science. | Tuldok must own the shared capability/evidence contracts and focused UI. | Baseline architecture against which the others are compared. Avoid duplicating existing ownership. |
| Embed/connect Label Studio or FiftyOne for annotation and model-error exploration. | Mature task-specific review, overlays and sample filtering can reduce UI work. | Existing model/prediction integration is required; backend/editor state must map to immutable Tuldok revisions and releases. Edition-dependent automation and another persistence/UI surface need review. | Consider a narrow adapter or component where it displaces concrete work. Do not replace authoritative release/family custody implicitly. |
| Use Lightning lifecycle hooks and/or MLflow tracking inside supported training adapters. | Reuses checkpoint/validation hooks, loggers, tracking and framework integrations. | Custom probe semantics still require integration; framework-specific support and versions vary. MLflow lineage digests can be metadata/sample-based, so are not substitutes for exact frozen bytes. | Evaluate as producer implementation options behind Tuldok's contracts, not mandatory product architecture or a second run authority. |
| Delegate whole workflows to a task platform such as Ultralytics; use declarative model configuration patterns such as Ludwig. | Guided defaults and integrated task-specific training/evaluation show how users avoid instrumentation chores. | Supported task/model families and runtimes constrain scope; configuration and model graph are different abstractions. Science-specific evaluation remains custom. | Borrow guided task/model definitions and resolved defaults. A full platform dependency requires a separately justified scope/custody decision. |

## Human-intent decisions to carry into design discovery

“Define a model” could mean choose and parameterize a template, compose supported modules in a graph, import a declarative configuration, or author arbitrary code. The design must compare these authoring levels and show one concrete user journey for each proposed level. Existing Pipeline graphs describe execution stages; they are not evidence that a neural-layer graph already exists. Recommend templates plus a declared custom-code escape hatch as a working design hypothesis, with a visual architecture editor evaluated explicitly rather than assumed.

Tuning also needs a product decision: a finite declared sweep and an adaptive search have different authorization envelopes. Current external grants bind exact material; changing parameters requires new material review. The design must compare (a) separately admitted trials, (b) an exactly enumerated approved batch, and (c) a prospective bounded study policy for adaptive choices. Runtime and total budget caps, permitted sources/parameters, stopping rules, observed-evidence use and user cancellation belong in that comparison. No existing grant should be interpreted as open-ended adaptive execution authority.

These questions should become explicit discovery decisions with recommended defaults and reviewable examples. They do not block designing the common evidence, capability and ownership model.
