## Existing model and evaluation seams

Model semantics currently live within each trainer, not in a standalone model catalog. `image_training.py:train` constructs the model, fits it, selects the lowest-validation-loss checkpoint, restores it, and writes final validation/test predictions plus history. Only the selected checkpoint and final per-example predictions survive; historic per-checkpoint outputs cannot be reconstructed. [image_training.py:298](../../../../image_training.py#L298), [image_training.py:381](../../../../image_training.py#L381).

The source identity is already authoritative: Pipeline hashes the actual local adapter import closure, including task readers and Workbench/access. Adding observation hooks changes that closure and therefore requires explicit version/compatibility handling; it cannot be presented as a chart-only change. [pipeline.py:432](../../../../pipeline.py#L432).

External execution already composes three concrete input kinds: observed project reference, frozen release and completed Run artifact. `recipe_contract.prepare` captures bytes through the appropriate owner and records typed input evidence. It does not need another generic artifact-reference mechanism. [recipe_contract.py:433](../../../../recipe_contract.py#L433), [static/workspace-external.js:4](../../../../static/workspace-external.js#L4).

Scientific evaluation is already a separate recipe consuming training checkpoint/freeze/inputs/result from one completed Run. Rheon owns mutual payload checks, native numerical meanings, field chunk retention and numerical acceptance. The generic core retains custody and process controls. New automatic scientific views should consume declared task evidence and preserve these meanings rather than promote arbitrary result JSON into scientifically verified metrics. [adapters/rheon/evaluate.py:32](../../../../adapters/rheon/evaluate.py#L32), [adapters/rheon/evaluate.py:207](../../../../adapters/rheon/evaluate.py#L207), [docs/contracts/rheon-evaluation.md:19](../../../contracts/rheon-evaluation.md#L19), [docs/contracts/rheon-evaluation.md:56](../../../contracts/rheon-evaluation.md#L56).

Live external progress is explicitly `live_unverified`; retained progress becomes `custody_verified` after receipt verification. A chart must preserve that distinction. It must not convert recipe-reported progress into an authoritative scientific result. [runs.py:563](../../../../runs.py#L563).

## Material promises to preserve or explicitly revise

1. Saved Pipeline drafts permit invalid semantics for editing, use checked revisions, and separate layout/name from execution identity. Run admission freezes the exact document and digest. New experiment/model configuration needs equally explicit revision and source identity. [pipeline.py:52](../../../../pipeline.py#L52), [pipeline.py:276](../../../../pipeline.py#L276), [runs.py:979](../../../../runs.py#L979).
2. Run submission reconciles an existing idempotency receipt before current graph validation; retries are new attempts and do not resume partial checkpoints. Trial scheduling must avoid duplicate admissions and distinguish retry from a new configuration/seed. [runs.py:944](../../../../runs.py#L944), [runs.py:1013](../../../../runs.py#L1013).
3. One `workspace_runs` supervisor, bounded queue, process identity/cancellation, unknown-state fencing and no restart replay are existing process promises. Tuning must not bypass them. [runs.py:80](../../../../runs.py#L80), [docs/contracts/workspace-runs.md:19](../../../contracts/workspace-runs.md#L19), [docs/contracts/workspace-runs.md:39](../../../contracts/workspace-runs.md#L39).
4. Completed means successful drained worker plus verified published artifacts, not accepted model quality. Publication is atomic; loss/tampering refuses artifact reads. Candidate acceptance needs its own domain result, not a new meaning for `completed`. [docs/contracts/workspace-runs.md:33](../../../contracts/workspace-runs.md#L33), [docs/contracts/workspace-runs.md:81](../../../contracts/workspace-runs.md#L81).
5. Existing internal classification outputs have an exact five-payload inventory and bounded closed progress events. Capturing additional checkpoints/predictions/diagnostics requires a new admitted evidence/adapter version and retention policy, not extra undeclared files. [image_training.py:417](../../../../image_training.py#L417), [docs/contracts/workspace-runs.md:76](../../../contracts/workspace-runs.md#L76), [docs/contracts/workspace-runs.md:88](../../../contracts/workspace-runs.md#L88).
6. Default evaluation is validation-only; test access records durable disclosure before return. Content/family exposure survives reimport/release changes. Automatic dashboards and tuning must not silently disclose or select on test evidence. [runs.py:1694](../../../../runs.py#L1694), [pipeline.py:378](../../../../pipeline.py#L378).
7. Historical targets/predictions remain frozen while corrections create current Workbench revisions. Viewer navigation must make both identities explicit. [runs.py:1719](../../../../runs.py#L1719), [workbench.py:476](../../../../workbench.py#L476).
8. External Projects remain reference snapshots; inspect/open does not execute, probe, install, deserialize or import. External execution consumes an exact owner grant, independently of ordinary automatic view setup. [projects.py:178](../../../../projects.py#L178), [runs.py:305](../../../../runs.py#L305), [docs/contracts/projects.md:114](../../../contracts/projects.md#L114).

## Five representative changes and expected propagation

| Change scenario | Required owner propagation | Must remain stable |
| --- | --- | --- |
| Correct a misclassified example and retrain | Linked evaluation view → current Workbench draft/review → new release → new experiment revision/trial → existing Runs admission. | Add a configurable model template or code-defined architecture | Model definition validates typed configuration/shape semantics and captures source identity → task compatibility → experiment revision → Pipeline execution material → trainer adapter → Run evidence. | Workflow nodes do not become model layers; arbitrary code does not become trusted through a template label. |
| Show the same validation probes across checkpoints automatically | Task/evaluation protocol resolves deterministic probes, inference settings and capture cadence → trainer observer emits checkpoint-bound artifacts → Runs verifies/publishes → evaluation query returns bounded evidence → linked view preserves example/time/scale. | Old Runs remain readable with historical predictions marked unavailable; test remains gated; live evidence is labelled provisional. |
| Tune learning rate and seeds, then compare candidates | Experiment coordinator owns trial definitions/budget/selection policy → deterministic idempotency keys → Runs queue → comparable evidence protocol → candidate decision with failed trials retained. | No second supervisor, hidden retries, test-driven tuning or confusion between retry attempt and trial. |
| Evaluate/export a scientific checkpoint on a qualified runtime | Candidate references verified checkpoint and preprocessing/model/task/protocol identities → evaluation recipe captures Run artifacts and runtime closure → task adapter verifies residual/field/time semantics → Run retains evidence → candidate package references accepted evidence and includes reproducible inference material. | Generic core does not redefine Rheon numerical acceptance; external project inspection remains inert; branch-only GPU support is not assumed. |

## New modules that earn their boundary

- **Experiment coordination** is justified: current Pipeline and Runs do not own a study's immutable revisions, comparable trial sets, tuning budget, selection policy or candidate decision. Its API should hide compilation, evidence-default resolution and trial admission bookkeeping. It references existing data/runtime/artifact owners.
- **Model definitions** are justified by the user requirement to author architectures independently from workflow recipes. They own versioned architecture/preprocessing/output compatibility and source identity; trained weights remain Run artifacts. Begin with bounded templates and captured code. A general visual graph editor is not prerequisite infrastructure.
- **Evaluation semantics and queries** are justified: checkpoint/probe identity, metric axes/units/direction, comparison compatibility, acceptance and task-specific view descriptors are not owned by current generic artifact custody. This module should validate and interpret evidence, with custody/publication staying in Runs. Split persisted evaluation protocol from derived UI descriptors; avoid a new viewer database.
- **Task capability definitions** are needed as a compact versioned contract shared by model compatibility, instrumentation and automatic views. They can be declarative definitions in existing task adapters rather than an independently persisted registry/service. Their exact placement must be decided from at least classification and scientific vertical slices.
- **Candidates** need a first-class immutable selection/package record eventually. They can initially be a focused part of experiment coordination if selection/export lifecycle is small; do not create a generic model registry merely to hold checkpoint aliases.

Avoid new dataset repositories, runtime managers, artifact stores, process supervisors, generic plugin frameworks, universal workflow engines or dashboard-configuration registries unless a concrete missing responsibility emerges. The central design issue is assigning one authoritative owner to editable experiment configuration and its compiled Pipeline snapshot, then introducing a reusable, task-aware observation/evidence contract. That supports automatic views without moving setup work onto each training user.

## Design decisions still required

Choose whether an Experiment embeds the authoritative execution configuration and produces immutable Pipeline snapshots, or references revisioned Pipeline drafts as its authority; do not permit two writable copies. Define the evidence evolution boundary for internal v1 trainers versus external recipes. Decide whether evaluation-only work is a distinct trial stage or linked Run type while keeping a single supervisor. Select the implementation baseline and reconcile the managed Torch branch before promising GPU/runtime automation. Finally, define candidate package compatibility and the exact treatment of holdout-sensitive scientific tasks, since current generic external recipes do not have the classifier exposure operation.
