The selected D1 journey

Candidate design

Read steps 01–08 in order. These are conceptual responsibilities; they do not require eight new services or screens.

  1. Build the dataset

    Import, generate, annotate, review, and retain family and provenance information.

  2. Freeze a release

    Record exact samples, annotations, split assignments, transformations, and exposure policy.

  3. Define task and model

    Use template forms and typed configuration, or captured project source. Keep computation meaning separate from workflow stages.

  4. Prepare finite trials

    Pin exact Pipeline material; resolve validation probes, selection criteria and aggregate budget. Exact authorization remains required.

  5. Execute through Runs

    Admit training and evaluation attempts through the existing execution owner.

  6. Evaluate automatically

    Open curves, fixed-example comparisons, task metrics, and declared domain checks as evidence arrives.

  7. Compare and select

    Inspect comparable trials, failures, validation criteria, and separate acceptance outcomes.

  8. Package a candidate

    Retain checkpoint, model and preprocessing definitions, output meaning, lineage, and evaluation evidence.

Two return paths: evaluation → dataset corrections → new frozen release; evaluation → model/settings changes → new experiment revision or trial. Historical evidence continues to reference its original inputs.

One recipe owner, one execution custodian

Selected D1 design

Pipeline edits; experiments pin; Runs executes

Pipeline alone owns editable execution recipes. Experiments retain exact recipe material and own trial membership, total budget and selection. Runs keeps admission, dispatch, cancellation and verified artifact custody.

Experiment intent→Runs→Verified evidence

Evaluation replay, tuning trials, and candidate verification must use the same owned execution path. D2 must specify retained pre-admission recipe snapshots and atomic study attachment; a bare reference to an overwritten draft cannot preserve a trial.

Automatic means integrated once

A task definition declares semantics, applicable metrics, and views. A trainer adapter emits the corresponding observations and retained evidence.

  • User chooses: task, dataset, model, and budget.
  • Tuldok resolves: compatible defaults, fixed validation probes, capture cadence, and viewers.
  • UI explains: pending, available, unsupported, failed, or omitted evidence.

Arbitrary custom code still requires an integration contract. Missing gradients, predictions, or physical semantics cannot be inferred from a final metric file.

Compatible agent operations, automatic observation

Required direction

Authorized agents complete the supported dataset-to-candidate workflow through discoverable interfaces. Metrics, checkpoint comparisons, error slices, probe predictions and bounded field values are available as structured evidence.

Clients negotiate exact supported per-operation contracts. New operations preserve unrelated compatible calls; incompatible mutations fail before domain entry. Current whole-registry equality needs a D2 migration and consumer disposition.

Observation runs behind ordinary operations: no extra logging tools, tracing arguments or per-run setup. Operators inspect permitted records separately. Interface observations, required domain audits and model-evaluation evidence keep their own owners and failure rules.

The MCP observer is integrated at main f58880df; reuse it first. D2 resolves transport coverage, operator policy, privacy, retention and overhead. Optional recording failure preserves domain outcomes; required audit failure follows its transaction contract. This is design direction, not activated collection.

Validation probes: visible during development

Fixed cases support checkpoint comparison, debugging, model selection, and tuning. Record their identity, selection policy, inference settings, units, coordinates, and shared scales.

Test evaluation: separately gated

Protected test families must remain outside routine tuning and probe galleries. Record access and exposure; a displayed failure may become a regression case but must not silently remain an untouched holdout.

Design phase checkpoints

Proposed sequence

Expand a phase to inspect its decision evidence. These controls describe design checkpoints, not implementation progress. Canonical phase names and acceptance criteria live in the plan.

D1Owner and task-path design

Selected: Pipeline recipe authority, template/configuration plus captured source, finite exact trials and compatible per-operation discovery.

Evidence: worked classifier and pressure-CNN paths, authoring edits, owner/change/deletion review and explicit current gaps. Read D1 design and independent review.

D2Reviewed contracts and cold evidence

Produce: versioned identity/evidence contracts, finite-trial permission and aggregate-budget/cancellation invariants, compatibility migration and cold readback.

Check: immutable recipe snapshots, atomic study attachment/reservation, scientific release bridge, honest missing history and current exposure policy before generic interface freeze.

D3Automatic capture and UI demonstration

Produce: a bounded walkthrough showing task-aware default views and linked checkpoint/example selection, plus capture, retention, and resource budgets.

Check: an ordinary user gets useful evaluation without configuring charts or callbacks; omitted evidence and unsuccessful model acceptance remain clear.

D4Tuning, runtime, and evolution handoff

Produce: detailed runtime scheduling under D2 invariants, runtime qualification, closed candidate packages, fresh-consumer inference acceptance and implementation slices.

Check: failed trials and repeated seeds are represented, tuning obeys exposure policy, and the handoff avoids a competing scheduler or speculative infrastructure.

Design examples

Existing image classifier

Review/freeze → TinyCNN widths 16/32/64 to 24/48/96 → exact recipe → authorized Run → automatic fixed validation probes → human/agent errors → corrected release or finite next trial → candidate package. Current v1 has fixed architecture and only best-checkpoint predictions; new authoring and probe contracts are still proposed.

Captured pressure CNN

Review/freeze fields → captured model/input/gauge edits → exact external grant → Adam training → checkpoint/field evidence → structured physics/error inspection → authorized next trial → diagnostic or qualified candidate. Prior training and restore evidence is real; physics qualification remained 0/16. The canonical-release bridge and recurring probes are still pending.

D2 contracts and remaining D3–D4 proof

Pending design and product proof
  • D2 foundations specified: immutable material and trial/attempt/replicate identity, atomic preparation/attachment, exact authority and stop-before-cancel epochs. Runs needs an outer-commit admission seam; reservation is accounting, not CPU/GPU/memory containment.
  • Compatibility selected: exact per-operation contracts with pre-domain checks, plus a frozen 56-operation legacy projection for supported strict clients. Inventory-owned retirement; no schema-subsumption engine.
  • Evidence contracts specified: versioned manifest/checkpoint/probe/field binding and bounded queries; retained v1 history stays absent. Standalone pressure fields have no invented physical frames. Scientific protected modes stay unavailable until every accessor protects mixed artifacts.
  • D3 still pending — interaction and costs: actual linked views, browser/keyboard/narrow-screen walkthrough and measured capture/retention/time/memory bounds.
  • Candidate closure: weights, model/source, transforms/fitted statistics, schemas/runtime, lineage/evidence and access. Later fresh-consumer fixed-probe inference must work without a live project checkout.
  • D4 handoff: detailed scheduling, runtime/dependency qualification, migrations and implementation slices. Adaptive prospective grants and a universal editable graph are deferred.
