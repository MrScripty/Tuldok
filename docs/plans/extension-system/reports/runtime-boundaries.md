# Tuldok extension runtime and data boundaries

Research date: 2026-10-15. Primary official sources only. Tuldok-specific statements are pinned to supplied PR62 source commit `f99182c03da1e070081718ef6829eaeac3c82640`; its implementation handoff identifies application main `f58880df` as the baseline and PR62 as unmerged. Existing external-recipe/Access/Runs contracts remain authoritative. New extension capabilities below are research proposals, not implemented behavior. The supplied contract snapshots were read; no repository changes, package installation, recipe execution, or runtime experiments were performed. [Tuldok implementation handoff](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/plans/end-to-end-model-development/reports/implementation-handoff.md).

## Executive recommendation

Reuse **Runs-controlled trusted-local execution**, with inert manifests, exact reviewed material, qualified captured runtimes and existing file/artifact custody. Do not introduce a second runner, supervisor, launch protocol or authority path. Any new worker-level schema negotiation belongs below the existing helper custody boundary. Let each trainer own its GPU context, model, optimizer, and batch loop only after its accelerator runtime is separately qualified; the current first path is CPU. Initially exchange CPU data and durable artifacts between admitted operations. Add faster transfer mechanisms only after a representative benchmark identifies the actual bottleneck. [Tuldok external recipes](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/external-recipes.md), [implementation handoff](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/plans/end-to-end-model-development/reports/implementation-handoff.md).

Label this honestly as dependency/crash isolation. Arbitrary Python running as the same OS user has that user's ambient authority. A manifest declaring `network: false`, a virtual environment, a subprocess, Python audit hooks, or omitted credentials does not make it a security sandbox. Python explicitly treats same-user multiprocessing peers as trusted and directs applications needing isolation to OS-level mechanisms. Python also warns that Python-level audit hooks cannot implement a sandbox. [Python multiprocessing](https://docs.python.org/3/library/multiprocessing.html), [Python audit hooks](https://docs.python.org/3/library/sys.html#sys.addaudithook).

The first product can safely state: “Run code you trust; Tuldok tracks what it ran and contains many failures.” It should not promise safe execution of malicious third-party code. If hostile-code execution is a requirement for the first release, platform-specific sandbox work becomes prerequisite work rather than a manifest feature.

## 1. Separate four boundaries

1. **Discovery boundary:** listing an extension must not execute it.
2. **Compatibility boundary:** protocol/schema negotiation decides whether host and worker can communicate.
3. **Custody boundary:** the host validates and commits dataset/run/artifact changes; workers return proposals and outputs.
4. **Security boundary:** only independently enforced OS/browser restrictions constrain malicious extension code.

These boundaries solve different problems. A worker can crash safely yet read all user files. A compatible worker can violate declared policies. A host can retain orderly database ownership without preventing same-user code from connecting to the database directly. Keep these distinctions visible in architecture documents and UI.

### Existing authority is unchanged

Availability and compatibility never authorize execution. External submission requires a live credential with inspect/execute scopes plus the exact actor/material one-use grant. Access rechecks current authority, grant expiry/revocation and consumption state under the owned lock; consumption, the Run's bounded continuation and audit commit together. Cancellation does not refund a grant. Reconciliation of the same actor/request key/exact request can return the existing committed attempt; it cannot silently authorize a fresh launch. An external retry requires fresh preflight, request key and approval. Built-in owner-only execution gates remain unchanged. [Tuldok actors](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/actors.md), [external recipes](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/external-recipes.md).

Credential revocation denies new submissions and other newly authorized operations. It does **not** cancel an already admitted Run: the retained closed admission may finish only its exact bounded effects after credential revocation. Revoking the approving credential also does not retroactively revoke an outstanding durable grant, although the consumer still needs live current authority at consumption. Explicit grant revocation prevents unconsumed use; consumed authority is controlled by cancelling its admitted Run, never converted back into reusable authority. [Tuldok actors](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/actors.md).

### PostgreSQL custody

Recommended contract: no application database connection object, superuser credentials, or unrestricted SQL API crosses the extension interface. Give recipes immutable snapshots/IDs and a scoped host API for the operations they genuinely need. Host validates ownership, dataset identity, revision, schema, output existence and sizes, then commits metadata in its own transaction.

This is a maintainability and consistency boundary in trusted-local mode, not a complete adversarial database boundary. PostgreSQL `peer` authentication derives database identity from OS identity. `trust` authentication allows anyone who can connect to select a database user; local TCP connections are not protected by filesystem permissions. Withholding a DSN therefore does not by itself protect a local database. Actual hostile-worker separation needs restrictive authentication/roles plus OS-level access separation. [PostgreSQL peer authentication](https://www.postgresql.org/docs/current/auth-peer.html), [PostgreSQL trust authentication](https://www.postgresql.org/docs/current/auth-trust.html).

## 2. Discovery and source import must stay inert

Recommended first path:

- Read a bounded JSON/TOML manifest using host-owned parsers. Record ID, version, entry target, supported operation kinds, config schema, data schemas, requested resources, and optional dependencies without evaluating Python.
- Importing a source directory means recording or snapshotting its files and hashing that snapshot, not importing its Python modules.
- Do not call a package's registration function, import it to read a constant, execute `--help`, install editable source, or build a wheel while merely listing extensions.
- Probe runtime capabilities only after entering the execution path, in the selected worker environment, with explicit timeout and a structured response.
- Do not mutate the host's Python environment or append untrusted directories to the host's `sys.path`.

PyPA entry points are static metadata in a distribution's `*.dist-info/entry_points.txt`. Resolving their object reference imports the target module. `importlib.metadata` separates entry-point attributes from `.load()`. Reading static metadata is useful; calling `.load()` crosses into execution. The import machinery can itself be extended, so strict source discovery should parse known files rather than run a candidate environment to ask it what is installed. [PyPA entry-point specification](https://packaging.python.org/en/latest/specifications/entry-points/), [Python package metadata](https://docs.python.org/3/library/importlib.metadata.html).

Installation and metadata generation are execution boundaries too: pip may call `prepare_metadata_for_build_wheel`, or build a wheel to obtain metadata. Its build isolation concerns dependency separation, not malicious-code containment. [pip build-system interface](https://pip.pypa.io/en/stable/reference/build-system/).

A subtle edge: even launching an installed Python to run a harmless metadata command can execute environment startup code. Python normally imports `site` during startup, and installed startup files/customization hooks can execute code before the requested command. `-I` changes import-path and environment behavior; it is not an OS sandbox. [Python site initialization](https://docs.python.org/3/library/site.html), [Python command-line options](https://docs.python.org/3/using/cmdline.html).

## 3. Environment capture is evidence, not portability

Preserve current qualified runtime profiles rather than accepting an arbitrary interpreter path. The current external-recipe `system_python` profile fixes `/usr/bin/python3` with `-I -S -B` and a bounded pinned runtime closure; installation ownership/permissions and runtime identity are checked. Workspace virtualenvs and arbitrary runtime paths are explicitly unsupported by that profile. Captured CPU projects retain their exact RuntimeSnapshots and source/runtime requirements. Runtime provisioning is separate; there is no install on open, preflight or worker start. [Tuldok external recipes](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/external-recipes.md), [implementation handoff](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/plans/end-to-end-model-development/reports/implementation-handoff.md).

A future runtime profile may use a declared Python constraint/lockfile, package sources and hashes, platform requirements and exact observed closure as inputs to qualification. Merely recording an existing interpreter or recreating a virtualenv is insufficient for admission. Such a profile needs an explicit contract, immutable identity/custody evidence and qualification; it cannot widen today's accepted runtime paths. GPU remains unavailable until separately qualified.

Python describes virtual environments as disposable and not movable/copyable. Capture dependency intent and recreate them; do not treat copying `.venv` as an export format. `pip freeze` reports installed packages and explicitly does not compute a lockfile or solver result. uv provides a universal, cross-platform dependency lockfile, and `--locked` prevents silently changing that resolution. None of these facts establishes that external tools, drivers, CUDA, OS libraries, network resources, or data paths exist on another machine. [Python venv](https://docs.python.org/3/library/venv.html), [pip freeze](https://pip.pypa.io/en/stable/cli/pip_freeze/), [uv resolution](https://docs.astral.sh/uv/concepts/resolution/), [uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).

Recommended provenance fields: source snapshot digest plus origin/commit and dirty-state evidence; manifest digest; protocol/schema versions; user config; actual negotiated capabilities; dataset revision and selected sample IDs; artifact hashes; interpreter and package inventory/lock digest; OS/architecture; trainer/framework/runtime and device/driver versions; random seeds and deterministic settings; attempt ID, timestamps, exit status and error category. Store environment variable names and selected non-secret values only; never dump the whole environment into provenance.

Differentiate three claims in UI/export metadata: “recorded enough to inspect,” “environment successfully reconstructed,” and “results reproduced within a stated comparison.” A lockfile and seeds alone do not prove the third. PyTorch explicitly does not guarantee identical results across releases/platforms or CPU/GPU. [PyTorch reproducibility](https://docs.pytorch.org/docs/2.14/notes/randomness.html).

## 4. Control plane and data plane

### Worker schema/data messages beneath existing custody

Keep the current private bounded helper socket protocol for READY, GO, cancellation and custody receipts. Recipe code must not inherit those control descriptors, and recipe stdout cannot declare completion. The following JSON/schema ideas are a proposed worker data-plane extension under that custody, not a replacement for READY/GO or a new launch channel. Prefer host-defined data messages over pickle, live Python objects, ORM entities or serialized callables. Separate diagnostics from any new structured data channel; bind messages to the admitted attempt and bound sizes, rates and outstanding requests. Existing `tuldok_progress_v1` and result-summary semantics remain authoritative until explicitly versioned. [Tuldok external recipes](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/external-recipes.md).

Negotiate supported operations, input/output schema versions, media modalities, CPU/GPU requirements, cancellation/checkpoint behavior and transfer formats. Distinguish **declared**, **observed** and **granted** capabilities. Reject missing required capabilities before starting expensive work. Unknown optional fields may be ignored only under a documented compatibility policy; unknown required capability/schema versions must fail closed.

### Data plane: smallest dependable choices first

**Encoded media and durable datasets:** pass immutable artifact IDs and host-resolved file references. Keep image/audio/3D bytes in their established file formats; avoid inventing a universal tensorized dataset representation. Text and sample metadata can use small JSON records initially. Describe image color space/orientation, audio sample rate/channels/timebase, and 3D coordinate system/units where relevant. An extension-specific media schema is acceptable when capability negotiation names it explicitly.

**Large CPU arrays:** start with numeric `.npy` files/memory maps or an existing project-native equivalent, with dtype, shape, layout, byte length, ownership and lifetime specified. Reject object-dtype/pickled data and validate dimensional/size limits before materialization. NumPy supports read-only memory mapping and warns that loading object arrays via pickle may execute code; `allow_pickle=False` is an important baseline, not a general malformed-file sandbox. [NumPy load](https://numpy.org/doc/stable/reference/generated/numpy.load.html).

**Columnar batches / large text metadata:** Arrow IPC files or streams are a good optional format when typed batched tables are needed. Its zero-copy reads depend on a suitable source such as a memory map or BufferReader; converting formats, decompressing, transferring devices or adapting downstream consumers may still copy. Arrow is a data format/transport component, not authority enforcement. Do not add Flight or a distributed service merely to use Arrow IPC. [Arrow IPC](https://arrow.apache.org/docs/python/ipc.html).

**Hot CPU batches:** shared memory can be an optimization after measuring file/mmap overhead. Host must own allocation budgets, lease/reference tracking, close/unlink cleanup and restart recovery. Define read-only-by-contract versus actually enforced access. Independent subprocesses introduce a Python-specific trap: their separate resource trackers can unlink shared memory when the first process exits. Python 3.13+ provides `track=False` for externally managed cases; Windows instead deletes shared memory after all handles close. Test the supported Python/OS matrix before choosing this transport. [Python shared memory](https://docs.python.org/3/library/multiprocessing.shared_memory.html).

### GPU transfer: keep ownership local initially

DLPack is a tensor interchange protocol between libraries sharing an address space, with ownership/lifetime and stream synchronization rules. It is not by itself cross-process IPC, a GPU scheduler, or a sandbox. PyTorch's DLPack conversion can alias the producer's memory, so in-place writes affect the other view. Use it inside a worker only when the two participating libraries and lifetime contract are known. [DLPack Python specification](https://dmlc.github.io/dlpack/latest/python_spec.html), [PyTorch from_dlpack](https://docs.pytorch.org/docs/stable/generated/torch.from_dlpack.html).

True GPU cross-process sharing is separate work. NVIDIA exposes explicit IPC memory/event handle APIs. PyTorch's CUDA multiprocessing sharing requires `spawn` or `forkserver`, producer lifetime through consumption, and careful release; abnormal consumer death can retain allocations. These are strong reasons to avoid cross-extension GPU sharing in the first path. [CUDA IPC memory APIs](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MEM.html), [PyTorch multiprocessing](https://docs.pytorch.org/docs/stable/multiprocessing).

Recommendation: a trainer process owns device allocation, model, optimizer, data loading and batch loop. A custom generator/evaluator can execute in its own process when it consumes/produces durable CPU artifacts; code that needs every training-step tensor runs as a trusted extension inside that trainer process under the trainer's dependency/trust boundary. Do not imply that an in-process callback is isolated from its trainer. PyTorch generally recommends pinned CPU memory instead of returning CUDA tensors from multi-process data loaders. [PyTorch data loading](https://docs.pytorch.org/docs/stable/data.html).

## 5. Resource, cancellation and failure contracts

Reuse the current Runs lifecycle and helper custody exactly. The bullets below identify extension obligations within it; they do not define a replacement terminal-state vocabulary or a process-group supervisor. [Tuldok external recipes](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/external-recipes.md).

- **Lifecycle and launch:** the sole Runs queue starts the pinned single-threaded Linux subreaper. Custody is established before READY; recipe children cannot start before GO. Runs commits exact helper identity and conservative `go_intent` before sending GO once. Unknown acknowledgement means no GO; restart never resends it. Extension negotiation/progress cannot transition the Run or mint another admission.
- **Cancellation and cessation:** preserve current controller-EOF cancellation and bounded drainage. The helper repeatedly identifies direct/adopted descendants, signals verified pidfds and reaps until spawning is closed and streams are drained. Only this exclusive helper's `ECHILD` proves cessation; a dead leader or empty process-group scan does not. A checkpoint, if separately supported, must be explicitly complete before being called resumable; no half-written successful result.
- **Unknown and fencing:** a missing/invalid drainage receipt after GO intent produces `unknown` and fences further external execution for that host boot. Acknowledging the error does not clear the fence. A later valid receipt or changed boot ID can prove cessation but cannot reconstruct successful completion. Detached sessions, double forks and ignored TERM remain within the Linux subreaper custody design.
- **Protocol failure:** distinguish invalid message/schema, unsupported capability, missing dependency, worker exception, timeout, out-of-memory evidence, user cancellation, unexpected exit, and host-validation failure. Preserve bounded diagnostics without exposing secrets.
- **Resource claims:** declare requested CPU threads, RAM, GPU device/memory estimate, wall time and output bytes. Report which are actually enforceable on the current platform. A CUDA device selection variable and framework memory setting should not be represented as hostile-code restrictions.
- **Backpressure:** bound in-flight batches and buffers; enforce a host acceptance budget even if the trusted worker misbehaves. Drain logs/control concurrently so a full pipe cannot hang a run.
- **Commit:** Runs independently validates approved output names/roles/files/sizes/hashes only after verified drainage and successful exit, then preserves its existing receipt/fsync/completed-state transaction sequence. Failed/cancelled/unknown attempts expose no successful result. Cancelled/invalidated/fenced attempts cannot acquire success through stale messages. Credential revocation alone does not invalidate the retained bounded continuation or its otherwise valid completion. External retries require fresh exact material/preflight/key/approval; do not assume external side effects are retry-safe.
- **Cleanup and recovery:** reuse current retained custody/receipt reconciliation and boot fencing. Do not automatically replay attempts, refund consumed authority or signal remembered foreign PIDs. Preserve ambiguous evidence rather than deleting it. Any new leased buffer needs cleanup integrated with this owner, not an independent recovery service.

Python's `Popen.communicate(timeout=...)` does not kill a timed-out child and buffers output in memory; `run(timeout=...)` has different kill/wait behavior. `terminate()`/`kill()` target the child, not an arbitrary descendant tree. Python's multiprocessing termination can corrupt queues/locks and leaves descendants orphaned. Choose the supervisor's behavior deliberately rather than assuming timeout equals full cleanup. [Python subprocess](https://docs.python.org/3/library/subprocess.html), [Python multiprocessing](https://docs.python.org/3/library/multiprocessing.html).

Cross-platform custody is future profile qualification, not current support. Windows Job Objects can manage descendants and apply resource limits with documented association/breakaway semantics; they are not a drop-in proof of equivalence to Tuldok's Linux subreaper receipts/unknown/fencing. Linux cgroup v2 provides resource controls when available and delegated; Python's `resource` module is Unix-only and platform-dependent. Current watchdog/output/admission limits are not aggregate OS quotas; required hard-quota modes remain unsupported under the handoff. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html), [Python resource limits](https://docs.python.org/3/library/resource.html), [Tuldok implementation handoff](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/plans/end-to-end-model-development/reports/implementation-handoff.md).

Revocation cannot erase data already read or undo arbitrary filesystem/network effects. Credential revocation denies new authority-bearing work, while an already admitted continuation retains only its exact bounded effects. To stop that Run use the existing cancellation/custody path; to block an unconsumed grant use explicit grant revocation. Current authority remains independently required at protected reads and new admissions. In trusted-local mode, filesystem/offline declarations do not remove ambient same-user authority. [Tuldok actors](https://github.com/MrScripty/Tuldok/blob/f99182c03da1e070081718ef6829eaeac3c82640/docs/contracts/actors.md).

## 6. Filesystem, network and secrets: be precise

Baseline hygiene: absolute executable, argument vector with `shell=False`, explicit working directory, minimal environment allowlist, closed inherited handles except intended channels, private per-run scratch, host-generated output locations, and no database/API secrets passed by default. These reduce accidental exposure and command injection risk; they do not strip the same OS user's authority. Check environment requirements such as Windows SystemRoot rather than erasing variables indiscriminately. [Python subprocess](https://docs.python.org/3/library/subprocess.html).

Treat extension-provided artifact paths and file formats as untrusted input even when the code is trusted for execution: reject unexpected locations/types, traversal and symlinks where not intended; validate sizes, schema, content and archive expansion limits; do not load executable serialization into the host to inspect it. Host custody should import finished regular files into host-owned storage. A path-prefix check alone is not a portable defense against symlink races. Strong containment needs platform-appropriate handle-based/OS enforcement.

Checkpoint inspection has its own code boundary. `torch.load(weights_only=True)` narrows the unpickler's behavior but does not prevent denial of service, and malformed values can be dangerous to later consumers. Never silently retry with `weights_only=False` to make an imported artifact work; full Python model/checkpoint execution belongs in the declared trusted worker path. [PyTorch serialization security](https://docs.pytorch.org/docs/stable/notes/serialization).

Cross-platform sandboxing is genuinely different work:

- **Linux:** Landlock can restrict filesystem and certain network operations, but supported rights depend on kernel ABI and configuration; feature detection and explicit policies matter. It is an ingredient, not proof that every socket protocol/device/GPU interaction is contained. [Linux Landlock](https://cdn.kernel.org/doc/html/latest/userspace-api/landlock.html).
- **Windows:** AppContainer is a security boundary constraining resources/network access. Job Objects are useful for lifecycle/resource management and should not be confused with that boundary. [Microsoft application isolation](https://learn.microsoft.com/en-us/windows/security/book/application-security-application-isolation).
- **macOS:** App Sandbox restricts filesystem, network and hardware through a signed application/entitlement model. Test actual Python/helper/native-library/GPU behavior and distribution model; do not assume a Linux sandbox plan ports by changing subprocess flags. [Apple App Sandbox](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox).

Minimal safe decision: ship one explicit trusted-local mode first. If a platform cannot enforce an advertised restriction, show it as unavailable rather than degrading silently. A later hostile-code tier needs its own threat model, supported-platform matrix and adversarial test suite.

## 7. UI extensions should start declarative

Prefer host-rendered configuration forms from bounded schemas, named commands, progress/metric events and artifact viewers selected by declared media/schema. No arbitrary extension JavaScript or Python-driven DOM injection is needed for the initial extension system.

If custom HTML/JS panels become necessary, treat them as a distinct execution boundary: separate origin/frame, sandbox, restrictive CSP, no filesystem/process/database APIs, narrowly typed host messages, validated sender/origin and explicit grants. A Python subprocess does not protect the host renderer from extension UI code. If Tuldok uses Electron, keep Node integration off, renderer sandbox and context isolation on, and expose individual validated IPC methods rather than a generic bridge. Electron warns that privileged preload APIs can defeat isolation; its docs recommend iframe sandbox capabilities and discourage the webview tag. These are conditional requirements, since the repository's UI stack was not inspected here. [Electron sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security/), [Electron web embeds](https://www.electronjs.org/docs/latest/tutorial/web-embeds/).

## 8. Small experiments that should decide the next steps

Run these only after separate implementation/execution authorization; none were run in this research.

1. **One existing external recipe round-trip:** inert source registration/preflight → captured qualified runtime/input material → exact current review/grant/admission → existing helper READY/GO → worker data/schema exchange if needed → verified drainage/output validation → Runs commit. Prove listing does not import code or create side effects. Keep a fixture with import-time writes to catch regressions.
2. **Fault/cancel matrix:** worker exception, invalid control bytes, log flood, stalled progress, crash during output write, DataLoader descendants, host/controller loss, missing drainage and stale completion. Acceptance: existing Linux custody reaches its documented completed/failed/cancelled or fenced-unknown outcome, without invalid commit or GO replay. Test that credential revocation denies new work while a previously admitted bounded continuation can finish. GPU and other OS cases belong to separately qualified future profiles.
3. **Representative transfer benchmark:** one real image batch, text batch, audio chunk and 3D asset. Compare current files/mmap to a bounded shared-memory implementation and Arrow only where appropriate. Measure end-to-end latency, throughput, peak RSS, copies and cleanup, rather than a zero-copy microbenchmark alone.
4. **Trainer ownership:** prove GPU initialization and CUDA work stay in the spawned trainer worker; measure cancellation and allocator cleanup. Avoid a CUDA-fork inheritance design. [PyTorch multiprocessing best practices](https://docs.pytorch.org/docs/2.14/notes/multiprocessing.html).
5. **Environment reconstruction:** take one CPU and one GPU recipe to a second supported machine; record what the lockfile reconstructs and what external requirements remain. Compare output with an explicit tolerance rather than promising bitwise equivalence.
6. **Policy honesty test:** in trusted-local mode verify what a worker can really read, connect to and spawn. If testing a later restricted mode, independently try forbidden filesystem paths, local PostgreSQL sockets, localhost services, network egress, inherited handles and resource exhaustion. The UI's enforcement report must match observations.
7. **Artifact trust test:** oversized array shape/header, object-dtype NPY, malformed Arrow/media, symlink output, path escape and unsafe checkpoint. Host must reject or quarantine without executing plugin-defined deserialization.

## Decisions still needed

- Current external recipes are explicitly trusted same-user code. Any future hostile-code/marketplace tier needs a separate threat model and qualified profile rather than changing this assumption implicitly.
- Current Linux CPU runtime/custody contracts and PR62's classifier-first qualification remain the baseline. Which additional runtime or accelerator profile has a concrete use case sufficient to justify separate qualification?
- Reuse existing Pipeline/RuntimeSnapshots/Access/Runs capture, one-use grants, subreaper custody, retained receipts and artifact publication. Which extension-specific schema or data exchange is still missing above those known seams?
- Which extension operations need streaming rather than durable artifacts, and which hot paths truly cross a process boundary?
- Are local PostgreSQL authentication and artifact-store permissions compatible with the intended trust tier?
- Which generated artifacts need to be shareable/reproducible elsewhere, versus locally traceable only?

The cheapest dependable path is to answer these with one real recipe and failure fixtures, reuse the current runner/storage system, and defer a marketplace, remote workers, generic RPC service, UI SDK, custom environment platform and GPU IPC layer until evidence requires them.
