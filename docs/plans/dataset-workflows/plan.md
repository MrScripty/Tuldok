# Dataset workflows

## Status and authority

Status: Active. Current phase: M1 verification and independent review. Acceptance: hosted automated evidence obtained; broader UI qualification and M2 remain open.
Canonical selection: `docs/plans/dataset-workflows/plan.md`, operation `start` for the user's authorized Tuldok development-branch expansion. This plan is scoped implementation authority, not authority to merge main or deploy.

The user prioritizes image/text annotation, dataset management/search/sort/analysis, and real or fully synthetic usable datasets. The UI is provisional. The dataset-production book's interactive examples are explicitly not the UI specification.

## Objective and scope

A person can use existing or imported image assets and text records, annotate and review them, select a corpus, understand measurable gaps, then freeze and validate a self-contained training-data release. Synthetic production uses that same lifecycle.

First slice supports image classification/axis-aligned detection and text classification/entity spans. Existing corner annotation, camera, and Pumas acquisition remain supported. Later model-assisted candidates and source-grounded transformations are required before claiming the overall expansion complete. No remote calls, new credentials, deployment, large models, or training runs are needed for the first slice.

## Constraints, binding decisions, and owners

- Isolation: `develop/dataset-workflows` starts at main `2fc4a46f12d73a0fa467d5482f68edb83d6df6af`; feature PRs target it. The root coordinator alone integrates after exact-head CI and applicable review. Main and the existing torch-provider integration branch are untouched. Retain the development branch for UI iteration; do not delete it at slice completion.
- Standards: MrScripty/Coding-Standards `dcc56f26e884ade260770beceba2501d3746200d`. Core plus routed implementation, discovery/planning, proportionality, commit, verification/oracles/GUI, documentation/tooling, frontend, persistence, contracts/evolution/protocols, architecture/replay, code design, security, concurrency, accessibility, dependencies/licensing and filesystem portability apply. No language-specific Python/JavaScript profile exists in that revision. Export data is consumed data, not generated executable schemas/bindings.
- Dataset owns image original/oriented bytes, image IDs and existing corner state. Workbench references those IDs, reuses image acquisition, and owns text records and generic annotation/review/history. There is no second image store. The same dataset lock/SQLite connection coordinates transactions.
- Boxes use oriented-image pixel-edge `[x,y,width,height]`, exclusive right/bottom bounds. Spans use Unicode code-point `[start,end)` offsets against stored canonical text. Empty objects/spans are reviewed negatives, not missing labels.
- Workbench records have protected group IDs and optional parent IDs. Source image revision and annotation revision are checked on mutation/release; stale results conflict rather than overwrite. Images generated by the existing Pumas path remain candidates until explicitly reviewed.
- Offline generators own versioned deterministic recipes and known targets, with seed, sampled factors and verification provenance. Programmatic verification never claims human review or real-world validity.
- Releases snapshot selected canonical assets, exact revisions, source lineage, frozen split allocation and vocabulary. Build ZIPs using bounded temporary files; publish only complete content-addressed archives via same-directory atomic rename. No live asset path determines an already published release. Backups include both SQLite/source assets and release files.
- This is a single-user trusted-local-data-directory application. The web caller is untrusted. Path IDs are allowlisted; no arbitrary import/export paths. Symlink mutation by another OS account is outside the inherited local deployment contract. Only Linux/Chromium acceptance is asserted here.

## Composed-design review: applicable

1. Image acquisition/storage/corner labels remain Dataset-owned; generic workbench annotation/text state belongs to Workbench; seeded generation belongs to recipes; split/release projection belongs to releases; HTTP and UI translate those contracts. Owners change for different reasons.
2. Asset ID, original hash and pixel geometry are stable; annotation revisions and review are mutable; a release freezes their relationship and split. Shared SQLite locking is necessary; UI-specific state does not enter persisted authority.
3. UI knows typed API actions and coordinates, not SQL/filesystem paths. Workbench knows Dataset's acquisition and image-reader contract. App composition creates/closes the shared lifetime. Export knows a captured record and asset stream, not mutable UI state.
4. Adding an annotation task changes its validator/editor/export projection and tests. Changing a generator changes its recipe and fixtures. A storage change affects Dataset/Workbench persistence, not label meaning. Changing layout is isolated to workbench static files.
5. Source IDs and revisions are explicit values. Sharing a connection/lock is an admitted internal storage composition, not a reusable plugin interface. No registries or generic adapter framework are added.
6. Domain validation and splitting test without HTTP; storage exercises SQLite; browser tests exercise real HTTP. Provider errors cannot publish accepted labels. Existing and new editors can conflict safely on source changes.
7. Without Workbench, new annotation/text rules would spread into the corner studio. Without recipe functions, asset/target derivation would enter UI handlers. Without release projection, mutable state would leak into export. A second image catalog and a universal modality abstraction are rejected by this deletion test.
8. Necessary complexity is provenance, coordinates, revision conflict, protected connected components and immutable export. Keep those within their owners. No queues, event bus, framework migration, schema generator, or cloud service is introduced.

Prove imported assets and generated pixels/text become reviewed/versioned records, coherent split allocations and valid exported data through the UI. Parent owns independent review and integration. No parallel writers to shared contracts or this plan.

### M2: model-assisted candidates and grounded transformations — Planned

Design against observed local provider capabilities and actual configurable source forms. Separate generated proposals from verified/human-reviewed targets; preserve provider/model/prompt/seed/source lineage, failures/cancellation/reopen, and train/evaluation ancestry. Use controlled providers for semantics; real inference is blocked until authorized and available. Exact write set and consumers are selected after M1; no claim of implemented model-assisted text generation now.

### M3: broader annotation/consumer support — Deferred

Owner: Tuldok maintainer. Revisit with actual mask, instruction-tuning, caption/retrieval consumers and UI feedback. Do not infer a universal segmentation contract from the training book's one binary-mask recipe.
