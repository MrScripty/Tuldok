What exists, and what changes

Verified main 2fc4a46 already preserves original images, oriented RGB pixels, book-corner labels, revision checks, manual splits, and resumable Pumas image jobs. The workbench will reuse that image acquisition/storage authority. Text assets and generic annotation revisions add capabilities rather than create a second image library.

First usable slice: image boxes and classes; text classes and character spans; measurable quality summaries; connected-family splits; frozen self-contained image detection and text releases.

Two ways in, one lifecycle

Real assets: import or choose existing images, enter/import text, identify protected groups, annotate, explicitly review, inspect distribution, and freeze a release.

Fully synthetic: offline seeded recipes create actual images and text with targets derived from the same scene/template state. Programmatic verification is visible and distinct from human review. These bounded fixtures demonstrate a functioning production path, not real-world usefulness.

Next slice: capability-checked model-assisted image/text candidates, configurable source material, proposal provenance, verification/review, and lineage-preserving transformations. Paid or live inference requires separate authorization.

Alternatives and consequences

  • Selected: reuse current image acquisition and storage, add workbench-owned annotation/text tables, publish immutable ZIP snapshots using bounded file streams. Avoids migration of existing corner data. Backups must include release files.
  • Rejected: a separate BLOB-backed image catalog. Atomic publication is attractive, but duplicate image ownership and whole-object memory pressure outweigh that convenience.
  • Deferred: replace the whole application with a framework and universal modality schema. That would delay usable image/text workflows and bind an unsettled UI too early.

Promises with boundaries

  • Boxes use oriented-image pixel edges, with exclusive right/bottom bounds. Text spans use Unicode code-point offsets with an exclusive end.
  • Protected groups and source ancestry stay together, including transitive relationships through unselected records. Ratios may be approximate; actual allocation is reported.
  • A release contains the selected asset bytes, exact annotation revisions, lineage, split, vocabulary, and contract. Later editing cannot change an old release.
  • Drafts and missing source data block release. Exact decoded-image/text duplicates and quality measurements are evidence, not proof of semantic diversity or generalization.
  • No segmentation, video, audio, near-duplicate clustering, distributed collaboration, or training-performance claim in this first slice.

Implementation decisions and acceptance belong to the canonical plan; this view is a discussion aid. Reopen the choice if actual source scale, consumers, annotation needs, or retention requirements invalidate these assumptions.
