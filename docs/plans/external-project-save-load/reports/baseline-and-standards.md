## Alternatives and deciding observations

1. **Whole-catalog JSON backup as Save:** rejected. It includes runtime/Access state, preserves one catalog identity, misses external roots and does not define project membership. Its readable container does not meet the user's authority/fork requirements.
2. **Export DB snapshots only when Save is clicked:** rejected. Acknowledged edits would be DB-only authority until Save and could be lost after a crash/database loss. A second unsaved authoritative store contradicts reconstructibility.
3. **Stable mutable record filenames plus multi-file recovery journal:** credible, but introduces a second recovery protocol because an old checkpoint could point to newly overwritten files. Default immutable revision files plus one current inventory reduce that obligation; their cost is retained text revisions and explicit manual inventory merges. Pruning/semantic merge are deferred.
4. **Keep catalog UUID in every independent fork or recursively rewrite IDs:** rejected. Shared mutable identity or changed historical material hashes would misrepresent evidence. Independent new active namespace plus inert origin-scoped facts preserves both.
5. **New project super-object owning science, models and execution:** rejected. Existing Pipeline/Models/Experiments/Runs/Access ownership is already selected by completed D1–D4 work; persistence packages their values without taking semantic authority.

No external service or numerical assumption must be tested to select these boundaries: the relevant code structure is inspectable. Actual local filesystem publication, projection cutover and Run barriers are future M1/M3 design observations with explicit stopping conditions. Their product acceptance remains pending.
