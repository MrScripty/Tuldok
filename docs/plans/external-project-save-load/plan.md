## Objective

A person can own a Tuldok project as an ordinary external directory, version its canonical plain-text records in Git, close Tuldok, and reopen it using a fresh runtime database. The directory retains authored work, annotations, scientific decisions, observations, exact historical material and lineage. PostgreSQL is a reconstructible runtime projection. Project-owned scripts supply domain integrations; Tuldok neither knows Rheon semantics nor runs scripts, installs dependencies or regenerates data on Open.

Save means a durable, coherent project checkpoint. A successful edit must also survive a process crash before the person clicks Save. Save As creates an independent project, retaining the provenance of inherited history without copying executable authority or falsifying old identities. Git alone transports text and manifests; large payloads require the explicitly listed external artifacts. Missing payloads remain visible and never become invented evidence.

## Scope

### In Scope

- Local, user-selected external directories on the currently supported Linux/POSIX local-filesystem deployment, using local PostgreSQL. The file format is portable text; writer support on other filesystems is a separate verified promise.
- One writable project per application workspace/session; separate projects use isolated runtime projections. Multiple browser tabs may share that owner with revision checks. Existing global/mixed catalogs remain a separately identified legacy mode until explicitly extracted.
- Project-owned editable data and history, saved selections/searches, Pipeline recipes, model definitions/materials, Studies/Trials/decisions, Run evidence and retained analysis, releases, project script/extension declarations, exact input and artifact manifests. Preserve all relevant closure, including cross-Study dependencies.
- New/Open/Save/Save As/Close, explicit relocation/rebinding, deterministic cold reconstruction, safe stopped extraction, consistent transport/UI behavior and the narrow lifecycle changes needed to keep project facts out of database-only authority.
- Git diff/commit/clone/checkout/manual merge workflows. Tuldok validates the resolved project and stale projection; it does not implement a Git client.

### Out Of Scope

- Any inspection, migration or execution of the user's local surrogate lab. Its local state is ahead of GitHub; GitHub is a code baseline only, never its current project truth.
- Unrelated product changes and Coding-Standards edits. A dedicated feature branch and draft implementation PR are authorized; incomplete milestones must not be merged as the completed feature. Any eventual merge requires relevant independent review, exact-head CI and acceptance gates.
- Repeating completed model-development D1–D4 architecture work, redesigning scientific metrics/training, adding a scheduler, domain-specific importer, universal object registry or recipe engine.
- Live export/fork during active or uncertain execution; collaborative/distributed writers, network-filesystem locking guarantees, semantic Git auto-merge, automatic conflict repair, cloud synchronization, automatic artifact fetch/install/regenerate, automatic garbage collection, automatic format upgrade/downgrade.
- Binary weights/data in Git, database dumps as the project format, and a promise that Git history alone backs up unique binary evidence. External artifact backup remains required.

### Canonical layout and versions

Proposed v1 layout, to be made executable in M1; names below are concrete defaults rather than implemented commands or schemas:

```text
my-project/
  .tuldok/
    project.json                 # sole current checkpoint / complete inventory
    records/<family>/<id>/<sha256>.json
    artifacts/<sha256>.json       # artifact declarations, not payloads
    history/<origin>/<family>/<id>/<sha256>.json
  scripts/                       # ordinary project-owned, inert on Open
  notes/                         # ordinary authored scientific notes
  artifacts/                     # untracked payloads, including unique evidence
  .tuldok-local/                  # ignored locks, resolutions, staging, runtime
  .gitignore
```

`project.json` uses a closed `tuldok_project_v1` format discriminator, project UUID, display name, optional fork-origin reference, explicit membership roots and sorted inventory entries. Each entry gives family, record ID, domain format, project/origin namespace, path, bytes and SHA256, with artifact/script/notes references as applicable. It enumerates everything needed to rebuild project facts and the explicitly external payload requirements. It must not become an umbrella domain version or authority: it references Workbench, Pipeline, Runs and Studies' independently owned formats.

Records are strict UTF-8 JSON with LF, deterministic key/order conventions and terminal newline. New project records use one documented serializer: sorted object keys, two-space indentation, finite JSON values, no duplicate keys, no Unicode normalization or unordered-array reordering unless the domain owns that equivalence. Authored strings keep their meaning. Immutable legacy evidence is a typed historical envelope containing the exact original document text and origin format/hash, so pretty printing never changes the source identity. A digest verifies exact bytes, not scientific validity. IDs, 64-bit counters and floating values must respect existing domain bounds; no lossy JavaScript conversion.

Immutable revision files allow a multi-record checkpoint to be published by replacing just `project.json` after all referenced records exist and are durable. Readers only traverse the inventory; arbitrary files and unreferenced partial objects do not acquire authority. A record filename digest is over its file bytes; existing material semantic hashes remain their domain hashes. Do not mix those equalities. Existing revision files remain retained in v1; reachability-based pruning is deferred. Inventory and file layout are Git-compatible text, although manual conflicts in the checkpoint inventory require resolution. No parallel stable-path copy of the same canonical records is introduced for prettier diffs. Inventory entries distinguish immutable domain/capture/evidence files from current user-editable scripts and free-form notes. A script or note used as historical input is captured immutably by its owning material/observation; its later working-file edits never change that capture. Prior captured/acknowledged note revisions remain in immutable records; current editable working inputs are not authority for past results.

`format` is the current project-format discriminator; per-family `format` preserves the domain contract; a projection schema/reader revision invalidates only the disposable projection; checkpoint digest is state identity; operation ID is retry identity. These values do not advance in lockstep. V1 supports only declared v1 project records plus explicitly selected historical source formats. Malformed content is `invalid`, a well-formed future format is `unsupported`, missing required content/capability is `unavailable`. Open never upgrades, drops unknown fields or downgrades. Future migration is explicit into a new destination, preserves originals and verifies its source/destination states.

Tracked defaults: canonical JSON, artifact manifests, authored scripts/notes and small explicit source/config inputs. Ignored defaults are anchored `/artifacts/`, `/.tuldok-local/`, virtual environments, caches, generated output, model weights and database/PGDATA directories. Do not blanket-ignore annotations or notes by extension. New writes stage only declared paths; Tuldok does not initialize Git, stage files or commit for the user. `.gitignore` is a convenience, not proof: status/checkpoint inspection identifies accidentally tracked generated/binary/secret-bearing paths without deleting or unstaging them.

### Stable identity and independent Save As

An ordinary move or Git clone preserves the project UUID, domain identities and checkpoint digest. A physical DB projection has a local instance ID and namespace/schema independent of that UUID; two locations with the same UUID do not share a mutable DB. Local binding keys include physical root identity and runtime instance; device/inode is a race/ownership check, never portable identity. Rebinding is explicit and leaves old registration snapshots intact.

For new projects, the existing logical `dataset_id`/catalog namespace can be the stable project UUID, avoiding a needless new semantic identity layer. `metadata.py` must separate this logical value from physical schema/runtime locking so clones have isolated physical stores. This is not permission to assign a mixed catalog's UUID to each extracted project.

Save As always makes an independent fork in v1. It copies validated canonical closure into a new non-overlapping destination with a new project UUID and fork-origin checkpoint. Existing historical material/Run/Trial identities remain scoped to their original namespace in an inert archive, including full ancestry and baselines. The archive is inspectable through new historical readers with explicit origin context; it is never inserted into active execution tables merely to satisfy existing `_load` joins. Copies of editable graphs/model definitions/selections receive destination IDs/revisions and explicit origin mappings. Re-preparation creates new material using destination identities through existing owners, with new approval if execution is requested. Existing historical material SHA256s stay unchanged. Legacy/forked historical Trials can be referenced as origins of new Trials without claiming same-catalog executable membership; the lineage contract needs an explicit historical-origin representation rather than weakening its current same-catalog validator.

Save As copies required unique binary artifacts to the new untracked payload area and verifies them before complete-copy success. Declared regenerable/large shared artifacts may remain external references with visible availability; copy policy and completeness are in the result. No writable hard links to source, no source destination overlap, and no overwrite/merge into existing projects. A metadata-only fork is explicit and cannot claim fully available evidence. A same-identity backup is a filesystem/Git backup procedure, not an ambiguous second Save As mode.

### Reconstruction and inert historical evidence

Open first reads a stable checkpoint and validates the entire referenced structural closure, then builds a fresh projection in isolated local storage and switches the session only after successful construction. The projection marker contains project UUID, exact checkpoint digest, projection schema/reader revision and local root/runtime binding. Partial projections never become ready. Missing artifact payloads are allowed for metadata/history inspection with explicit per-artifact unavailable status; missing canonical records fail Open. Ordinary Open may create derived SQL/index files, but causes no project-script import, subprocess launch, dependency installation, network resolution, data generation or automatic model/material preparation.

Project mode also has one process-wide workspace/session controller, not one active project per tab. Every request carries the opaque local binding handle (project UUID + local binding instance + session generation); the server pins and authorizes that exact binding before dispatch. A global mutable `dataset` alias is insufficient. `make_handler(dataset, ...)` currently closes over one Dataset; project-mode routing must resolve a guarded binding through the controller while legacy mode keeps its fixed Dataset. Read responses carry that generation; queued mutations from the old binding are rejected before effects, never redirected to the new project.

New/Open/reload may validate an incoming checkpoint in isolation, but replacement uses the same Close gate: preflight unsent form input, close old admission, drain pending requests/commits/jobs/descendants, reject active or unknown cessation, and only then atomically install the new binding and release the old resources. In-flight old responses cannot apply to the replacement UI, and a closing binding cannot accept later mutations. A failed incoming validation or Close gate leaves the previous project selected and its custody owned; a created but unselected New destination is reported by exact creation receipt rather than mistaken for a successful switch. T6/T8 must cover delayed old reads/mutations, concurrent tabs, active jobs and failed replacement.

The current `Dataset` constructor calls job recovery and `Runs._recover`. Add an explicit inert composition path before calling these owners: history readers and query projections are separated from live runtime reconstruction. A stored Run terminal state is a historical fact. Stored active/unknown state is an observation of the old machine, not a request to attach to its PID or resume; unresolved local work remains controlled by its original runtime owner. An imported history record cannot enter `_recover`, consume an old request key or open a Study epoch.

Retain immutable facts needed to interpret evidence: reservation-to-Trial/Run association, exact approved material and approval time/disposition, producer inputs, consumed-charge history, lineage/baseline edges, selection decisions, measurement definitions, source/runtime declarations and artifact digests. Retain opaque attribution identifiers only as historical labels; credentials/tokens/token hashes, private endpoints and active session IDs are excluded. Grants/consumptions/admissions are represented as inert typed historical facts with no authorization capability, never restored into `access_*` runtime tables. Run specs/custody files require field-level classification: exclude executable continuation control, but preserve exact signed/hashed evidence fragments and required non-secret proof in an inert envelope. If a source format inseparably binds a secret into evidence, extraction reports it and stops that record pending an explicit preservation/redaction decision; it cannot silently alter proof or put secrets into Git.

Historical readers reuse owner validation of values/integrity while dropping the requirement for *live* reservation/grant rows. They still check complete historical proof closure and current local disclosure permission. Where proof is missing, show retained/unverified or unavailable, never a new verified/accepted status. This distinction is necessary because `runs.py` currently joins reservations, grants and consumptions to validate external Run history. Newly measured regeneration results get new artifact/Run/observation identities and explicit derived-from links. Even byte-identical output cannot silently replace the original measurement's provenance.

### Durable mutation, Save and recovery

Avoid distributed SQL/file commit as two equal authorities. In project mode, a mutation uses the existing domain owner to validate against the current checkpoint/projection, constructs its changed canonical records and stages required new payloads. Under the project writer guard, it rechecks expected checkpoint and domain revisions, durably publishes immutable records/payloads, then atomically publishes the new checkpoint containing the operation receipt. Only the canonical commit authorizes success. SQL applies the committed change afterwards or is rebuilt; failure after canonical commit is reported as committed/projection-unavailable with exact checkpoint/operation identity, never as permission to repeat the effect. The next command must reconcile/rebuild before mutation.

A staging transaction may use SQL rollback for validation, but cannot acknowledge DB-only domain facts or dispatch execution before canonical commitment. Existing audit/receipt guarantees must be preserved in that boundary: portable non-secret audit facts commit with the project mutation; local credential audit references stay local. This is a coordinated project-mode change to existing mutation owners, not a generic decorator around arbitrary SQL writes.

Save validates the latest committed closure, waits for pending project publications and fsyncs the checkpoint barrier. It returns project UUID, checkpoint digest, completeness/missing-artifact summary and receipt identity; no-op Save preserves canonical bytes. Forms not submitted remain UI input: navigation/Close warns about them, while submitted edits are already durable. This avoids a persistent DB-backed “unsaved project” with an implicit second authority.

| Interruption window | Required reopen / retry behavior |
| --- | --- |
| Before record/payload durability | Old checkpoint remains authoritative. Preserve or remove only proven task-owned incomplete staging; no success acknowledged. |
| After immutable files, before checkpoint replacement | Old checkpoint remains authoritative; orphan files are inert and retained for diagnosis. Retry checks operation identity and input revisions. |
| During checkpoint replacement/fsync, or lost acknowledgement | Outcome is unknown until the actual checkpoint is reread. Its atomic old/new content plus embedded receipt decides commitment; no guessed rollback or duplicate effect. |
| After checkpoint durability, before/during SQL update | New checkpoint wins. Rebuild derived projection; acknowledged work survives. Never roll files back to match SQL. |
| During New/Save As/extraction destination publication | Stage on destination filesystem, verify full inventory/required bytes, fsync, publish a non-existing destination atomically, fsync its parent. Receipt resolves lost replies. Source remains unchanged. Unsupported rename/durability capability refuses publication. |

Rebuilding or replacing a projection is permitted only after accounting for original local custody. Do not drop a projection/control binding while active or unknown workers still own it; close/fence and prove cessation first, or remain blocked. Losing SQL cannot grant new execution permission or erase unresolved local work.

No automatic recovery deletes canonical history, overwrites a conflicting destination, or retries project code. Keep recovery bounded and operator-readable; no new general journal/event-sourcing engine is needed. The checkpoint's current operation receipt and retained operation records provide the retry window required by public clients; preserve request scope/body binding and reject changed-body key reuse. Retention and expiry rules belong to the new operation contract; old execution request keys never become imported retry authority.

### Active runs, Close and multiple writers

One local process owns a writable project binding and all effectful child work. Use a kernel-released local file lock for physical root ownership and existing catalog coordination within that runtime; a lockfile's age or PID text alone cannot authorize takeover. Each mutation additionally compares the expected canonical checkpoint and domain revision. A second writer gets `busy` with no effects; an optional metadata reader reads an immutable checkpoint. Copies/clones on separate local directories are independent workspaces sharing history; Git integration is explicit.

All durable authored/Run lifecycle facts needed after database loss must reach canonical records, including admission intent, measured outcomes, publications and interruption observations. High-rate progress may remain disposable diagnostics if labeled so. Execution permission/lease remains local and is never reconstructed from those facts. M3 must place the Run dispatch barrier after the canonical admission fact and current local approval checks; canonical history alone cannot authorize GO. Worker completion must publish artifacts and final evidence durably before reporting terminal success.

Save can checkpoint a project during an active Run only after draining currently committing facts; it clearly reports active custody and is not a portable live snapshot. Save As and extraction require closed admission and proven cessation of all relevant descendants/publication work, including generation/proposal jobs. Unknown cessation refuses them. V1 Close similarly returns `busy` until the user explicitly stops work and the owner drains it; Close never kills unknown PIDs, silently cancels, discards edits or detaches workers. On ordinary crash/restart, only the exact original local runtime may reconcile live custody under existing rules; inert Open on a fresh runtime does not resume anything. A missing old runtime cannot be interpreted as proof that a former process ceased; execution readiness remains fenced where local unresolved effects could still act on the same root.

### Git changes, stale projections and conflicts

Support Git checkout/merge while the project is closed. For deliberate edits to current scripts or free-form notes, offer an explicit `adopt_working_files` operation: inertly report changed declared editable paths and their old/new identities, require the expected project/checkpoint and explicit selected changes, validate bounded regular files and any owned declared structure, then capture changed bytes and publish a new canonical checkpoint. Retain prior acknowledged/captured versions and record the edit origin; any source/material preparation remains a separate action. Deletion of an editable note is a retained tombstone, not history removal. External edits are unacknowledged input until adoption; no promise recovers bytes the external editor itself destroyed before any capture/Git backup. Show this distinction without hiding the new bytes.

Adoption must never update hashes for changed immutable records, captured sources, materials, Run outputs, artifacts or historical envelopes to make corruption pass. Such edits require restore from an authoritative source or an explicitly new domain record/measurement with new identity. Validate-only has no write effects; adoption is a separate explicit mutation, not auto-repair on Open/Save. If editable-file drift prevents a normal Open, an owner may select that project into an inert validation/adoption context without installing it as a ready writable workspace; publish a validated new checkpoint before normal Open. This recovery path has the same root/permission/current-session replacement gates and cannot relax immutable closure validation.

Changes outside the application while open invalidate the checkpoint binding: before each mutation and authoritative query, compare the bound inventory checkpoint identity and verify the referenced records being consumed. If changed, return `stale_project`, fence mutations, retain the old projection for diagnosis and require explicit reload after resolving UI input. No automatic Save overwrites a checkout. Read paths label their captured checkpoint and cannot mix data from new files with old SQL. Immutable filename/byte mismatches are corruption; never repaired by trusting the DB.

Unresolved Git entries or conflict-marker/malformed referenced JSON block writable Open; structural closure also detects duplicate IDs, broken references, stale hashes and conflicting project identities. A `.git` file in a worktree is not a directory assumption; use Git's declared plumbing for optional unmerged-entry detection, with no hooks or filters executed. Format validation remains mandatory without Git installed. Manual merge resolution includes updating the inventory's paths/hashes and checking semantic constraints such as acyclic lineage and release/material references. Provide a pure validation/report command rather than a semantic merge engine or automatic winner. A destructive old checkout need not retain later history; the current checkpoint defines current state, with later committed text/payloads recoverable from their own backups. Never garbage collect artifacts just because a branch no longer references them.

An advisory lock does not fence a concurrent Git client or malicious filesystem writer. V1 requires closed-project checkout and rejects observed changes; it does not promise transactional live Git edits. Detect record changes across read/validation/publication using rooted handles/identity checks and final expected-checkpoint comparison. If a concurrent non-cooperating editor defeats the supported preconditions, preserve both staged material and conflicting checkpoint for explicit recovery; do not report a successful overwrite. Supporting hostile/uncooperative distributed writers would require a different coordination contract and is deferred.

### Artifact resolution and narrowly scoped protection

Each artifact declaration gives a stable identity, SHA256, byte size, role/media/domain format, owning record, provenance/producer inputs, required-for operations, and retention class: unique evidence, captured source/input, regenerable generated output, or disposable cache. Include the generic recipe/source/runtime/input identities describing regeneration, never an Open-time action. A local resolution maps digest to project-relative payload or operator-selected approved root; absolute paths, credentials and device/inode stay untracked. Reject changed bytes as integrity mismatch and never search arbitrary host paths or fetch a URL on Open. File-size/hash work is bounded/streamed and cancellable; index reading need not hash terabytes before metadata inspection, but actual consumption verifies required bytes through the artifact owner.

Preserve original unique annotation/source/observation bytes through transfer and backup. Original bundle bytes currently in PostgreSQL BYTEA are externalized to untracked payloads with exact digest/size, not base64 embedded in Git metadata. Tiny human-authored annotations/decisions remain text; large numeric observations may be payloads whose unique evidence status requires backup/copy. “Generated” never implies disposable when the particular measured result is historically irreplaceable.

Threat model: a locally selected project contains untrusted records/scripts; browser/agent input must not authorize arbitrary host writes; cooperative local writers can race. Reuse rooted no-follow handle traversal and regular-file checks, rejecting absolute/traversal components, symlink escapes, special files and unsafe creation/replacement. Check destination non-overlap by filesystem identity/components, not string prefixes. Reject hard-link alias overwrite for owned canonical writes and avoid writable hard-link copying. Bounded strict decoding and inventory size/depth/byte limits prevent accidental resource exhaustion; choose limits from admitted current record bounds and a representative fixture, rather than reusing the 64 KiB registration manifest limit for a whole project. Display paths/diagnostics must not leak DSNs, credentials or unrelated host locations. Project scripts remain inert text and previews escape markup. No new sandbox, cryptosystem or network service is justified by save/load itself.

## Migration And Extraction

This is an explicit future procedure, not startup migration and not authorization to touch the real lab. Preserve existing backup/restore unchanged for whole-catalog disaster recovery; it contains Access/runtime authority and only the managed catalog file tree, so it is not the portable project format.

1. **Report only:** against an owner-selected, supported, quiesced catalog, inventory requested roots and complete transitive dependencies. Today registration has no authoritative ownership mapping. Report shared records, ambiguous membership, excluded unrelated projects, missing external-root payloads, cross-Study parents/baselines, source/artifact/rights constraints and unknown source formats. Use a disposable representative fixture first.
2. **Resolve closure:** user selects which workflows/Studies/records belong; include immutable referenced facts even from other Studies as read-only provenance. Do not infer ownership from names or copy every table. Retain provenance mapping `(origin catalog, family, ID, revision/hash) → destination record/history` and per-family counts/hashes plus exceptions. Unsupported/secret-entangled records block complete extraction rather than being skipped.
3. **Freeze source:** stop all writers, close admission, prove worker/descendant/publication cessation and retain a verified whole-catalog backup plus separately inventoried external roots. The existing backup excludes external roots; explicitly preserve their required bytes. Read-only discovery never fences or modifies a running user catalog by surprise.
4. **Create destination only:** new project UUID; extract editable records through domain-owned codecs, archive exact historical material with origins; move BYTEA contents to immutable payload files and copy unique ordinary files. Do not mutate/delete/re-sign the source catalog, rewrite old hashes, mint review facts or reactivate approvals. Extraction receipt ties source revision/inventory, mapping, chosen scope and destination checkpoint together.
5. **Verify cold:** reopen from text/manifests and declared payloads with no source DB, paths or runtime control. Compare authored annotations/decisions, deletion/history/exposure, Study/Trial/Run associations, costs, lineage and artifact identities against the independently read source fixture. A report of row counts alone is insufficient.
6. **Cut over explicitly:** user chooses new project after reviewing proof and outstanding missing artifacts. Keep original plus backup read-only until retention decision. Roll back by reopening the original under its compatible binary; retain all new project writes for explicit reconciliation. Never discard post-cutover work by restoring an older backup over it. No dual-write period.

## Simplicity And Ownership Review

**Applicability:** `applicable`

- Independent concepts and dimensions: the user chooses *what* belongs in a project and *where* it lives; domain owners decide values/scientific meaning; project store owns *how/when* coherent records become durable; Access owns *who may act now*; Runs owns execution/custody; projection adapter indexes facts. These change for different reasons. An inventory packages them without acquiring their semantic policy.
- State, identity, value, time, policy, and mechanism: project UUID is a logical scope; origin material identity is immutable history; root inode and physical DB ID are local mechanisms. Checkpoint digest binds values at a state; observed times/approval facts do not imply present permissions. Project format, domain format, projection revision and operation key each own a different promise. Current project-v1 writers/readers agree; unknown future formats reject. Existing registration v1/v2 and selected history readers coexist because actual stored inputs exist, not as an indefinite global compatibility matrix. A note edit invalidates its record/checkpoint and SQL view, not old model hashes; a new model prepares new owned material.
- Caller and composition-root knowledge: callers select root/project/action and expected revisions, receive durable identity/outcome/completeness, and handle stale/busy/unknown states. They need not serialize SQL, determine transitive closure or rewrite catalogs. App composition supplies the store, isolated projection and inert/history versus live runtime owners. This ordering must be centralized rather than repeated in UI/CLI/MCP.
- Representative change paths and forced owners: annotation correction touches Workbench canonical revision and new release/trial only if explicitly requested; model edit touches model/Pipeline material and new references; relocating a folder touches local binding, not historical identity; artifact cache move touches resolution only; adding an observation format touches its owner/reader, not project UUID or all formats; adding a transport action projects the same operation contract. Unexpected changes across unrelated authorities trigger replan.
- Stable Interfaces versus hidden knowledge: store exposes open/commit/save/fork/close plus immutable checkpoint inputs; domain codecs expose owned values/closure and validation. Internal SQL table names remain projection details. Historical origin readers expose inert proof, not a fake Access implementation. Rooted filesystem and artifact handles carry capabilities; public clients do not learn `.tuldok-local` or PG schema names. Material ordering/failure obligations are explicitly part of the interface, not hidden behind “save”.
- Independent evolution, testing, failure, and replacement: PostgreSQL projection can be dropped/rebuilt on matching checkpoint; historical readers can reject an unsupported format without changing notes or running jobs. Domain formats evolve explicitly without an unrelated umbrella increment. Missing artifacts disable their consuming operations while text/history remain inspectable. File commit can succeed when SQL update fails; result makes that fact explicit and gates later actions. A new DB engine is not promised or needed to establish reconstructibility.
- Necessary complexity and containment: multiple authoritative records need a durable publication boundary; legacy identity-bound evidence needs an inert namespace; subprocess effects need their existing lifecycle owner. Keep these in store/history adapters and existing Runs, with explicit closure, rather than adding a distributed transaction service, event bus, scheduler or generic plugin registry.
- Deletion and cumulative machinery result: deleting the store spreads durability/checkpoint/stale checks into every adapter; deleting domain codecs loses meaning or makes the store a second interpreter; deleting history separation either leaks live authority or destroys evidence; deleting artifact manifests hides unique/missing bytes; deleting physical writer ownership permits lost updates. Immutable revision files + one checkpoint remove the need for a second recovery journal/generation database. Extraction is a bounded explicit command, not a permanent synchronizer. No extra registry, version per field, semantic merge engine, always-on watcher or generic integrity framework is admitted. Existing whole-catalog backup remains for its distinct recovery promise, never a second project format.
