# Software precedents for integrated training evaluation

Checked 2026-10-15 against official documentation. These examples support a connected annotation → dataset → model configuration → training → evaluation → correction workflow. They also establish an important boundary: automatic behavior follows a supported task/model integration. Arbitrary training code, scientific fields and native solver checks still need explicit adapters. These are architectural precedents, not proposed dependencies or independently tested products.

| Precedent | What the software provides | Defaults and integration boundary | Implication for Tuldok |
| --- | --- | --- | --- |
| **Label Studio — annotation platform with model backends** | Connects a model server to annotation tasks, displays predictions for review, and starts training manually, through an API or via webhooks. | Requires connecting/implementing an ML backend with the needed prediction/training capability; many supplied examples cannot train. Its guide distinguishes Enterprise automated active learning from Community manual sorting and prediction retrieval. Prelabeling must be enabled. [ML integration guide](https://labelstud.io/guide/ml.html). | Keep predictions, corrections and retraining connected to the same data identities; expose model capabilities explicitly. Annotation events can nominate a new training release without silently changing old runs. |
| **PyTorch Lightning — training toolkit** | Trainer manages training/evaluation lifecycle, logging and checkpointing; callbacks expose validation batch/epoch, prediction and checkpoint hooks. | Last-epoch checkpointing is enabled by default. Users supply the Lightning model/data/validation logic and emitted metrics. Best-metric checkpoint selection, fixed probes and visual artifacts require chosen callbacks/configuration. A framework hook does not infer the meaning of an arbitrary model's outputs. [Trainer 2.6.6](https://pytorch-lightning.readthedocs.io/en/2.6.6/pytorch/common/trainer.html), [callbacks 2.6.6](https://pytorch-lightning.readthedocs.io/en/2.6.6/pytorch/extensions/callbacks.html). | Attach evaluation instrumentation to the training lifecycle once per supported adapter, so ordinary users receive recurring evidence without writing log calls for each run. Keep the adapter's task semantics distinct from the generic run host. |
| **MLflow — experiment tracking and evaluation platform** | Tracks metrics/models/artifacts and dataset name, digest, source lineage, schema and usage context. Dataset examples distinguish training/validation/test and target/prediction columns. | Autologging is explicitly enabled before fitting and varies by supported framework. The documented PyTorch autolog route supports Lightning, not every handwritten Torch loop. Explicit `log_input` records other datasets. Lineage metadata is not a universal immutable snapshot: metadata-only datasets do not hash data, and evaluation digests may sample rows. [Autologging](https://mlflow.org/docs/latest/ml/tracking/autolog/), [dataset tracking](https://mlflow.org/docs/latest/ml/dataset/). | Make instrumentation automatic within admitted recipes and show dataset/model/run lineage together. Preserve Tuldok's exact frozen bytes and SHA-256 custody instead of substituting a generic tracking digest. |
| **Ultralytics Platform — integrated vision workflow** | Guided dataset/model selection, training and browser testing; training charts and validation confusion/PR/F1 views when corresponding artifacts exist. Data tooling includes annotation and statistics. | Users select a supported task/model/dataset and training configuration. Saving a linked dataset snapshot is an explicit option in the checked guide. Model YAML describes task-specific backbone/head layers; custom modules require code integration. [Quickstart](https://docs.ultralytics.com/platform/quickstart), [data preparation](https://docs.ultralytics.com/platform/data), [model YAML](https://docs.ultralytics.com/guides/model-yaml-config). | A guided integrated product can hide instrumentation chores while retaining explicit model/data/configuration choices. Declarative architecture is a useful precedent; these docs do not establish a universal visual neural-network editor. |
| **Ludwig — declarative model/training toolkit** | A single configuration describes inputs, outputs, preprocessing, architecture, trainer, hyperparameter search and execution backend. | Input/output feature definitions are required; other sections have defaults. Supported feature/task semantics drive model construction; this is configuration-driven software rather than evidence of arbitrary architectures working without integration. [Configuration guide](https://ludwig.ai/latest/configuration/). | One validated training definition can connect UI choices to a reproducible executable model and its expected evaluation capabilities. |
| **FiftyOne — dataset/model evaluation workbench** | Per-example evaluation results, confusion-matrix filtering and detailed error analysis link metrics to source examples. | Existing predictions and an explicit evaluation operation are needed. The coordinating review verified SDK-driven evaluation in open source and App/background evaluation in Enterprise; this is not automatic retraining. [Evaluation guide](https://docs.voxel51.com/user_guide/evaluation.html?highlight=evaluation), [advanced analysis](https://docs.voxel51.com/getting_started/model_evaluation/02_advanced_analysis.html). | Extend the existing metric → exact-example → correction loop, retaining frozen targets and declared evaluation results. |

The first five rows were checked directly during this research; the FiftyOne distinction was checked against those official sources by the coordinating review. This note makes no claim that any single example already combines all Tuldok requirements, or supplies scientific validity automatically.

The resulting design recommendation is a unified task/model definition and an evaluation-capability contract. A supported recipe should automatically produce its declared metrics, checkpoint/probe artifacts and lineage; the UI should expose suitable views from those capabilities. Unsupported telemetry remains explicit. Domain adapters supply native residuals, field alignment, conservation, uncertainty semantics and acceptance rules. Human review and data correction feed a new frozen release and run, preserving prior evidence and test exposure. This recommendation concerns Tuldok's architecture; adopting any named package is a separate decision.
