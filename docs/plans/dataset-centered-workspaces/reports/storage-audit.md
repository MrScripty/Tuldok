# Local-first metadata amendment and source audit

Scope: planning only, following the user's clarification that a database service on the same machine is acceptable. No database was installed, migrated or exposed, and no credential, runtime or CI change was made.

## Decision and reason

Use **PostgreSQL as the intended authoritative metadata store, initially local**, with ordinary local files for image/release/new large run artifacts. Qualify migration and local lifecycle in MB before M2 adds graph/run persistence. M1's fixture UI remains independently deliverable. Do not build two production backends without a demonstrated need; retain SQLite as an untouched legacy import/rollback source subject to write-preservation rules.

This follows the actual coupling audit and the user's preference to avoid substantial later rework. A local PostgreSQL service satisfies local-first: no external network is required after installation. A future shared server can use central PostgreSQL, but clients still need an authenticated application API, authorization, revision conflicts and worker ownership. Changing a bind address is not collaboration support. No local S3, Redis, distributed leases or sync engine is proposed.

The delegated read-only audit found 145 direct `execute` calls across 16 production modules, 64 connection-context scopes, and `.db` access in 30 of 37 Python test modules. The publication author independently reproduced these three counts using Python AST over root `*.py` and a `.db` scan over `tests/test_*.py`. The reviewer also identified SQLite-specific facilities in 21 test modules. The MB write set also includes `native_text_import.py`, which owns a connection context and catches `sqlite3.Error` even though it has no direct `execute` call. These counts demonstrate distributed coupling; they are neither an effort estimate nor evidence that each call needs a new abstraction.

## Qualification hazards and preservation gates

| Hazard | Required disposition before cutover |
| --- | --- |
| Connection and transaction lifetime differs | SQLite connection contexts commit/rollback without closing; psycopg connection contexts also close, and statements including SELECT normally begin transactions. Give connection, outer transaction and nested savepoint lifetimes explicit owners; test nested imports, read-only preview rollback and failures after commit. Do not translate `with db` mechanically. [Psycopg transactions](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [connection context](https://www.psycopg.org/psycopg3/docs/basic/usage.html#connection-context). |
| SQL, schema and ordering are SQLite-specific | Convert placeholders/errors, catalog checks, table rebuilds, JSON operations and `rowid` ordering deliberately. Preserve observable ordering with explicit data; do not infer it from unordered PostgreSQL rows. Version schema and retain unsupported-source-schema preflight. |
| Exact persisted text/evidence is meaningful | Preserve exact strings and serialized evidence where hashes or consumer contracts require it. PostgreSQL JSONB changes representation, so blanket JSONB migration is invalid. PostgreSQL text cannot store NUL; current SQLite data may. Select a lossless representation and prove roundtrip, or stop before cutover; never strip or silently normalize. [PostgreSQL character types](https://www.postgresql.org/docs/current/datatype-character.html), [JSON types](https://www.postgresql.org/docs/current/datatype-json.html). |
| Process-local locking is not DB concurrency | Two independent connections must prove revision-checked stale-save refusal, idempotent admission and lost-ack recovery. Choose explicit snapshot/locking/atomic-write semantics for each owner; default Read Committed is not a drop-in proof of an entire release snapshot. Retry only the bounded DB transaction where safe, never replay external inference or published effects blindly. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html). |
| Embedded assets and files have different publication/backup behavior | Preserve existing mesh/sequence bundles as byte-exact `bytea` initially; keep existing image/release files and paths. Stage/publish/reconcile new run artifacts under one managed directory; incomplete file+metadata outcomes remain explicit. [PostgreSQL binary data](https://www.postgresql.org/docs/current/datatype-binary.html). |
| Backup and rollback must preserve all user data | Keep source application writers and artifact mutators quiesced from the final consistent SQLite+file snapshot through verification and the authority switch. Import into a new DB from the untouched backup, compare all owners, and switch only after a real restore/workflow proof. If cutover fails, resume the untouched source. An online migration needs a separately admitted delta-capture/reconciliation design. `pg_dump` covers a database, not artifact files or cluster roles; record full restore prerequisites, versions and role/privilege setup without secrets in Git. After post-cutover application writes, reconcile/export them before rollback; stale SQLite alone cannot preserve them. [SQLite backup](https://www.sqlite.org/backup.html), [PostgreSQL dumps](https://www.postgresql.org/docs/current/backup-dump.html). |
| Tests currently depend on SQLite internals | Use isolated local PostgreSQL databases/connections in future CI. Replace SQLite-specific mutation/introspection mechanisms with equivalent contract assertions; keep legacy SQLite migration fixtures. Do not delete difficult negative cases or weaken acceptance. |

MB's migration matrix includes current and older supported catalogs, every metadata owner, IDs/revisions/history, deleted lineage, rights corrections, proposals/admission receipts, exact strings/JSON and byte/hash equality. The real browser import/edit/review/select/preview/release/reopen/proposal-recovery path must pass. Local server/driver packaging, startup/shutdown/reopen, least-privilege loopback/socket defaults, supported versions and full backup/restore must also pass. PostgreSQL's network capability alone closes none of these gates.

Small metadata, artifact and application-command boundaries are required because their current lifetimes differ; they do not promise cost-free portability. The intended PostgreSQL choice remains subject to executable qualification, not a claim that migration has happened. No duration promise is derived from source counts.
